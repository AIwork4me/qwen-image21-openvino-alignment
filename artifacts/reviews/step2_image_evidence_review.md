## 6. Methodology (single pipeline, identical latents)

`scripts/benchmark_suite.py` (read in full):
- Pipeline is constructed once per invocation (line 45) and reused for all arms/prompts/steps; `true_cfg_scale=1.0`, no negative prompt, `prompt_embeds` injected from the frozen NPZ tensors.
- Per-seed latent is regenerated deterministically (`torch.randn` on a CPU `Generator` seeded by the seed, lines 78–85) and hashed into the manifest; the same tensor object is reused for every prompt/arm/step of the invocation.
- `os.path.exists` skip logic (line 94): pre-existing images are not regenerated and get no manifest row.

`artifacts/logs/canary40_3way.log` confirms one process for the new arms: a single "suite complete canary 20 gens in 802.5 s", per-prompt interleaved lines `[C0x s20261001 40s O3qL] … [C0x s20261001 40s O1]` for all 10 prompts; manifest gen_s values match log lines (e.g., C01 O3qL 42.199 s ↔ "42.2s").

`artifacts/metrics/suite_canary_manifest.json` internal consistency (current, 20 rows, O3qL/O1 × 10):
- All rows: seed 20261001, steps 40, latent_hash = 976e549d… (single distinct value) — identical to the R0/O3r seed-20261001 rows in the HEAD manifest and to the trace runs.
- pe_hash: 10 distinct values per arm (one per prompt, as expected). I recomputed two rows from the NPZ tensors using the exact runner code path (`prompt_embeds_bf16_view` → float32 → unsqueeze → sha256 of dtype+shape+bytes): O3qL/C01 → a19eb01b… ✓ exact, O1/C10 → 9796d5f5… ✓ exact. All 20 referenced PNGs exist on disk.
- Note on the brief's caveat: the current manifest was NOT rebuilt — it carries genuine gen_s timings; it is the direct output of the Oct 4 run. The HEAD version *was* a filename rebuild (gen_s = null, latent_hash null for seeds 20261002/03) and, notably, used a **different pe_hash convention** (2D `prompt_embeds`, no unsqueeze — verified: R0/C01 2D hash = 1d3f5e54… matches HEAD rows) than the live runner (3D). Cross-manifest pe_hash values are therefore not directly comparable.

Methodology caveats (warnings, not failures):
1. The R0 reference images compared against O3qL/O1 are the files from the Oct 3 R0/O3r invocation (file mtimes Oct 3 17:41–18:03; no R0 lines in the Oct 4 log). "One pipeline instance" is literally true for the O3qL+O1 arms of the three-way suite; R0 comparability rests on the deterministic per-seed latent (hash-verified identical) and identical pipeline config, across processes. This is acceptable but should be stated as such.
2. Latent is shared per seed (one latent for all 10 prompts), which is the intended frozen-input design.
